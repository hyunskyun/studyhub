# 플랫폼별 배포 전략 — Windows/iPad 웹앱 + Android APK

- 문서 상태: 2026-11-20 사용자 추가 배포 요청 반영. Q1~Q157 선택을 바꾸는 것이 아니라 **산출물/패키징 전략**을 추가한다.
- **목표**: Windows PC와 iPad는 동일 웹앱(Cloudflare Pages)을 사용하고, Android 스마트폰은 설치 가능한 APK를 사용한다.
- **핵심 원칙**: React + Vite + TypeScript 프런트엔드, 화면, 라우팅, 도메인 타입, 계산, 서버 API를 공유한다. Android는 Capacitor 프로젝트로 빌드한다. 별도 React Native 앱은 만들지 않는다.

## 1. 플랫폼별 산출물

| 기기 | 실행 형태 | 배포·설치 | 업데이트 |
|---|---|---|---|
| Windows PC | 브라우저 웹앱 | Cloudflare Pages HTTPS URL | 웹 배포 시 반영 |
| iPad | Safari 웹앱, 선택적 홈 화면 PWA | 동일 HTTPS URL / 홈 화면에 추가 | 웹 배포 후 브라우저/PWA 캐시 갱신에 따라 반영 |
| Android 스마트폰 | Capacitor 기반 앱 | Android Studio/Gradle에서 생성한 설치형 APK | React/네이티브 코드 변경 시 새 APK 빌드·설치 필요 |

공통 Cloudflare Pages Functions 또는 Workers API + Cloudflare D1에서 사용자별 데이터를 제공한다. Google 계정의 사용자 ID는 PC/iPad/Android에서 일관되게 매핑한다.

## 2. 권장 저장소 구조 (예시; 실제 프로젝트 검사 후 조정)

```text
my-ipad-app/
  src/                  # 모든 플랫폼이 공유하는 React UI, 라우트, 기능, 도메인
    components/
    features/
    services/
    platform/           # web/android 인증·스토리지·시스템 뒤로가기 어댑터
  public/
  docs/
  android/              # npx cap add android 실행 후 Capacitor Android 프로젝트
  capacitor.config.ts   # webDir: dist (Vite 기본값일 때)
  vite.config.ts
  package.json
```

Android UI도 동일한 **하단 내비게이션**을 사용하고, iPad·PC 웹은 **사이드바**를 사용한다. 개발자 도구/기기 너비만으로 네이티브 앱 여부를 판별하지 않고 필요 시 `Capacitor.isNativePlatform()` 같은 플랫폼 API를 사용한다.

## 3. 권장 개발/패키징 순서 (Q157A 유지)

1. 현재 React/Vite 프로젝트 검사(`package.json`, 설치 상태, 빌드, 기존 화면, Git 작업 트리).
2. 기존 확정 기능명세를 따라 모든 화면/컴포넌트/디자인 시스템을 **웹 프리뷰로 먼저 완성**. 새 사용자 기본 화면은 빈 상태이며 테스트용 mock은 분리.
3. 사용자 디자인 검토 후, 호환되는 Capacitor 버전 선정 및 Android 빌드 환경 확인. 개발용 Android APK로 동일 UI의 실기기 동작 검증. 이 단계는 Google 로그인/Drive/D1 연결 완료가 아님.
4. IndexedDB/Dexie 등 공통 로컬 repository, 핵심 규칙·로컬 CRUD·타이머·오프라인 검증 구현. Android 저장 데이터 보존 가능 여부를 실제 APK에서 검증하고 필요 시 네이티브 지속 저장 어댑터 검토.
5. Cloudflare 서버/D1/Google 웹·Android 로그인 및 계정간 동기화 구현. Drive 파일 선택/권한 동의를 플랫폼별로 검증.
6. Windows 웹·iPad Safari/PWA·Android APK 사이 로그인, 크로스디바이스 동기화, 타이머 소유권, 오프라인 충돌, 백업/복원 E2E 완료 후 최종 웹 배포 및 APK 릴리스.

## 4. Capacitor 기본 명령 예시

먼저 실제 Node.js, Android Studio, Java, Android SDK, Capacitor 버전의 호환성을 확인하고 기존 설정이 없는지 확인한다. 기존 `@capacitor/*`가 있다면 중복 설치·초기화하지 않는다. Vite 기본 출력 디렉터리가 `dist`일 경우를 가정한다.

```powershell
# 기존 웹 프로젝트 루트에서 실행 (개발자/Claude Code가 검사 후)
npm install @capacitor/core @capacitor/android
npm install --save-dev @capacitor/cli
npx cap init
# capacitor.config.ts에서 webDir: 'dist' 확인 또는 설정
npx cap add android
npm run build
npx cap sync android
npx cap open android
```

- `npx cap add android`는 한 번만 생성하며 이미 `android/`가 있다면 재실행하지 않는다.
- 웹 코드를 변경한 뒤 Android 앱에 반영하려면 **다시 `npm run build` + `npx cap sync android` + Android APK 빌드**가 필요하다.
- 초기 개발에서는 Android Studio에서 debug APK를 빌드·설치해 검증한다. 일반 배포용 APK는 별도 서명이 필요하며 keystore 비밀은 저장소/채팅/클라이언트 번들에 포함하지 않는다.
- Android APK는 기본적으로 빌드한 웹 자산을 패키지에 포함하도록 설정한다. 운영 앱이 매번 원격 웹 URL을 직접 띄우는 원격 WebView 방식(`server.url`)은 기본안으로 사용하지 않는다.

## 5. Google 로그인·Drive 권한에서 반드시 분리할 부분

- **웹(PC/iPad)**: 웹용 Google 로그인과 웹 앱 origin/redirect를 이용한다.
- **Android APK**: 삽입형 Android WebView 내부에서 Google OAuth 로그인 창을 띄우는 방식은 금지된다. 지원되는 Android 네이티브 로그인 API 또는 **시스템 브라우저 기반 인증(Custom Tabs 등)** 및 안전한 복귀(deep link/redirect) 방법을 사용한다. Google Cloud Console의 Android OAuth 클라이언트는 패키지명, APK 서명 인증서 지문 등 플랫폼 요건을 따른다.
- 두 플랫폼 모두 로그인 결과를 **서버가 검증**하고 동일 Google 사용자 계정에 매핑한다. 플랫폼별 획득 토큰과 API 인증 세션은 보안 모델을 구분하고, Android WebView 내 쿠키가 PC/iPad 웹과 공유된다고 가정하지 않는다.
- Google Drive는 앱 로그인과 **별도 OAuth 동의**. Android에서 Drive 파일 탐색/선택, 권한 재요청, 파일 열기 흐름을 실기기로 검증한다. 웹 Google Picker를 Android WebView에서 무조건 똑같이 실행할 수 있다고 가정하지 않는다.
- 앱 소스 및 APK 안에 비밀키, 장기 갱신 토큰, 서비스 계정 JSON, 백엔드 관리 API 키를 포함하지 않는다.

## 6. 오프라인과 업데이트 규칙

- 모든 플랫폼에서 서버 데이터 원천은 **Cloudflare D1**, 클라이언트는 로컬 캐시 및 변경 큐를 사용한다.
- 웹은 IndexedDB/Dexie 기반. Android에서도 WebView의 IndexedDB 동작·생존성을 시험하며 저장소 생명주기가 적합하지 않으면 공통 repository 인터페이스 뒤에서 Android 전용 영속 스토리지 어댑터를 도입한다.
- 계정당 활성 타이머 1개, 플랫폼 간 권한 이전 확인, 오프라인 충돌 후보 보존 등 이미 확정된 동기화 규칙은 동일하다.
- 브라우저 웹앱의 배포 업데이트가 이미 설치된 APK의 웹 코드까지 **자동 업데이트해 주지는 않는다**. 새 앱 버전을 빌드하고 동일 package ID/서명키로 업그레이드 설치해야 한다.
- Android 기기에 직접 APK를 설치(사이드로드)하려면 기기의 설치 허용·보안 경고가 발생할 수 있다. 앱 스토어 출시를 원할 때는 스토어별 패키징/서명/심사 규칙을 별도로 검토한다.

## 7. 필수 테스트 체크리스트

- 공통 반응형 UI: Windows 1440x900 / iPad 834x1112 / Android 390x844 근처 뷰포트.
- Android: 앱 설치, 재실행, 업그레이드, 뒤로가기, 키보드 가림, 상태바/내비게이션 안전 영역, 터치 제스처, 다크 모드.
- Android: 네트워크 끊기/재연결 후 로컬 기록 보존 및 D1 반영, 타이머 계속/휴식 검증.
- 웹 ↔ APK: 같은 Google 계정 로그인·사용자 분리, Google Drive 권한 별도 부여, 30일 휴지통, JSON 백업/복원, 학습 기록 시간 충돌 없음.
- 운영/릴리스: 웹 배포와 APK 배포는 다른 산출물임을 문서화; debug/release 서명과 버전 관리 구분.
