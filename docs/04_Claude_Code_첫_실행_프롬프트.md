# Claude Code 첫 실행용 프롬프트 — 웹앱 + Android APK

> 아래 구분선 사이의 내용을 프로젝트 루트에서 실행한 Claude Code에 그대로 전달하세요.
> 먼저 이 패키지의 `01_통합_기능_명세.md`, `02_설계_결정_추적표.md`, `03_Claude_Code_개발_계획.md`, `05_플랫폼별_배포_전략.md`를 **프로젝트 루트의 `docs/` 폴더**에 복사합니다.

---

당신은 개인 학업 통합 웹앱 및 Android APK 프로젝트를 이어서 개발하는 시니어 프런트엔드 엔지니어이자 제품 디자이너입니다. 새 프로젝트를 만들지 말고 **현재 작업 디렉터리의 기존 프로젝트를 직접 분석한 뒤 작업**하세요. 이 프로젝트는 사용자가 확정한 157개 기능 결정과 이후 추가된 배포 플랫폼 요구사항을 따릅니다. **Windows PC·iPad에서는 웹앱, Android 스마트폰에서는 설치형 APK를 사용합니다. UI와 로직은 React 단일 코드베이스를 공유하고 Android APK는 Capacitor로 제작합니다.**

## 가장 먼저 반드시 읽을 문서

1. `docs/01_통합_기능_명세.md` — 요구사항 최종 통합본. 실제 동작 규칙과 예외의 기준.
2. `docs/02_설계_결정_추적표.md` — 질문 1~157의 최종 결정 추적표.
3. `docs/03_Claude_Code_개발_계획.md` — 단계·검증 게이트·QA 기준.
4. `docs/05_플랫폼별_배포_전략.md` — PC/iPad 웹앱, Android APK 패키징·로그인·저장소·검증 정책.
5. 저장소에 존재하는 `CLAUDE.md` 및 관련 개발 지침(존재한다면).

문서 경로가 다르거나 누락되어 있다면 탐색해 보고, 문서 없이 추정하여 기능을 구현하지 마세요.

## 사용자가 확정한 현재 개발 원칙

**이번 작업의 최우선 목표는 디자인 및 전체 화면 완성입니다(Q157A). 기능·DB·인증·동기화 연동은 UI 디자인이 완성되고 사용자가 확인한 뒤에 진행합니다.**

**배포 구조는 웹앱 + APK입니다:** Windows PC·iPad는 Cloudflare Pages 웹앱, Android 스마트폰은 동일 React/Vite 빌드 산출물을 Capacitor로 패키징한 Android APK. 별도 Android React Native 앱을 새로 만들지 마세요. 플랫폼별 인증·스토리지·뒤로가기 등의 차이는 어댑터로 처리하세요. Android Google OAuth는 삽입형 WebView 안에서 직접 실행하지 않습니다. APK 배포 및 네이티브 설정은 UI 디자인이 완성된 이후 별도 검증 게이트로 진행합니다.

- 기존 프로젝트를 최대한 보존하세요. 과거 맥락상 React + Vite + TypeScript, Tailwind CSS v4, vite-plugin-pwa, lucide-react, recharts, Dexie를 사용하려고 했지만 실제 파일을 읽어 확인하세요.
- 미니멀한 정보 설계, 반응형, 라이트·다크·시스템 테마 지원(Q154B).
- **Android APK 스마트폰** 하단 내비게이션, **iPad·PC 웹앱** 사이드바(Q153B).
- 캘린더 기본은 **일간 보기**(Q152A).
- 실제 신규 사용자에게는 샘플 데이터·필수 설정 없이 **빈 상태부터 시작**(Q155A).
- 앱 내부 노트 편집기·모의고사 파일 첨부·일반 할 일 반복 기능을 임의 추가하지 마세요.
- 고정된 학습일 기준: `Asia/Seoul`, 매일 05:00. 홈의 오늘·D-Day도 05:00 기준(Q52–55, Q156A).
- **실제 학습 기록 간 중복 시간 확정 저장 금지(Q84 최종 수정)**. 이는 UI 검증 상태와 나중의 서버 검증에 모두 반영해야 합니다.
- 학습 **시간 목표에는 자습만** 포함하고 학원 수업은 통계에서 별도로 집계(Q70A).
- 30일 휴지통, Google Drive 원본 삭제 금지, 시험 기록에 Drive 파일 연결 금지를 유지하세요.

## 1단계 — 저장소 실사(첫 작업)

1. 현재 작업 경로, `git status`, 전체 디렉터리 구조, `package.json`, TypeScript·Vite·Tailwind·PWA 설정, 현재 엔트리/라우트/컴포넌트·디자인 시스템을 확인하세요.
2. 설치되어 있는 도구로 기존 `build`, `lint`, `test`(존재하는 것만) 실행하여 기준 상태를 기록하세요. 없는 스크립트를 실행했다고 주장하지 마세요.
3. 기존 파일과 컴포넌트를 유지·재사용할 수 있는지 판단하고, 사용자 결정과 충돌하는 기존 코드가 있다면 목록화하세요.
4. 무엇을 왜 변경할지 간단히 안내한 뒤 **전체 UI 단계**를 실행하세요. 사용자가 이미 UI 우선 개발 순서를 승인했으므로 추가로 동일한 승인을 반복 요구할 필요는 없습니다.

## 2단계 — 디자인 시스템과 모든 화면 구현(이번 작업의 핵심)

### 디자인 기준
- 과도하게 화려한 스타일보다 명확한 정보 위계, 높은 가독성, 일관된 간격, 정제된 타이포그래피를 우선하세요.
- 테마 변수·디자인 토큰을 일관되게 정의하고 라이트/다크에서 상태 색상 대비를 확인하세요.
- iPad의 터치 사용을 고려하되 PC 마우스·키보드 상호작용도 편하게 설계하세요. Android APK에서 시스템 뒤로가기, 소프트 키보드, 안전 영역(Safe Area), 터치 사용 및 WebView 뷰포트도 고려하세요.
- 임의의 색상·디자인이 사용자 결정으로 확정된 것처럼 표현하지 말고, 제안한 디자인 시스템은 작업 요약에 명시하세요.

### 제작해야 할 화면
- 홈 대시보드(오늘의 시간표, 우선 표시 시험·수행평가, 할 일, 목표, 타이머 요약)
- 일간 캘린더(시간 블록, 드래그 편집 UI, 학교·학원 수업 일정, 반복 일정 UI)
- 일반 할 일/하위 체크리스트(우선순위, 부분 완료, 완료 목록 접기)
- 학습 타이머·학습 기록(과목 전환 설정 확인, 휴식, 잠금 후 재확인, 기기 이전 확인, 시간 충돌 편집 화면)
- 문제집/중단원/Part(일괄 붙여넣기 UI, 진행률, 일괄 완료)
- 모의고사/성적/오답 분석/재응시 비교(오답 완료 확인 포함)
- 학교 지필 시험/시험 범위/연결 문제집 진행률
- 수행평가 프로젝트/세부 단계/제출 상태/획득 점수
- 학원 강좌/출석/휴강·보강/주간 숙제/템플릿
- 학교 현재 시간표
- 목표 및 학습 통계(자습/학원/전체 분리, 과목·기간·태그 필터)
- Google Drive 연결 자료(접근 불가 상태 포함)
- 이름 통합 검색(보관 기록 포함 옵션)
- 보관함·30일 휴지통·삭제/복원 대화상자
- 설정/Google 로그인/Drive 별도 권한/JSON·CSV 백업 UI

### UI와 실제 기능을 구분하는 방법
- 이번에는 **화면 구조·컴포넌트·라우팅·UI 상태 전환 및 입력 검증 표시**에 집중합니다.
- 서버 API/D1 마이그레이션/실제 Google OAuth/Drive 접근/실제 기기간 동기화는 아직 구현하지 마세요.
- 모델 데이터 타입, repository 인터페이스, mock adapter를 만들어서 나중에 실제 구현을 교체하기 쉽게 하세요.
- 화면 디자인을 검수할 개발 전용 fixture를 격리하고, 실제 신규 사용자 상태는 **0건**으로 시작하세요. fixture를 사용자 데이터로 자동 삽입하지 마세요.
- 실제 동작하지 않는 버튼에 성공 토스트를 표시하지 마세요. 프로토타입일 경우 UI 미구현/연결 예정임을 개발 모드에서만 분명히 하세요.
- 기존에 이미 구현된 실제 기능이 있다면 파괴하지 말고 필요한 범위에서 UI와 연결을 유지하세요.

## 검증과 결과물

- 실제로 존재하는 검사 스크립트를 사용해 빌드·타입·린트 검사를 수행하세요.
- 가능하면 현재 저장소의 브라우저 자동화 도구로 **390×844, 834×1112, 1440×900** 뷰포트에서 스크린샷을 만들고 레이아웃 붕괴/잘림/접근성 문제를 확인하세요. 사용 가능하지 않으면 불가하다고 정확히 보고하세요.
- 라이트/다크, 신규 사용자 빈 상태, 많은 항목이 있는 개발용 fixture 상태를 각각 확인하세요.
- 페이지마다 기본 탐색, 모달·필터·폼 UI, 오류 상태의 일관성을 확인하세요.
- UI 작업 도중 D1/Google OAuth/실제 외부 서비스 설정을 요청하거나 생산 환경에 배포하지 마세요. 이후 웹 UI 검수 게이트에서 Android용 Capacitor 패키징 및 **개발용 APK UI 검증**까지 실시하되 서버 기능이 구현된 것처럼 표시하지 마세요.
- 모든 UI 변경 후 다음 정보를 보고하세요:
  1. 수정·생성 파일과 디자인 시스템 핵심 규칙
  2. 구현 완료 화면 목록과 남은 디자인 작업
  3. 실행 가능한 개발 서버 명령 및 미리보기 방법
  4. 직접 수행한 웹 빌드·린트·테스트 결과 및 Android APK 패키징 가능 여부(실제 검증 여부 구분)
  5. 검토해야 하는 UI 화면/상호작용 및 디자인 결정이 필요한 부분
- **사용자가 전체 UI 디자인을 승인한 다음에만** `docs/03_Claude_Code_개발_계획.md`의 2단계 이후 실제 데이터·DB·인증·동기화를 연결하세요. Android SDK/Studio가 갖춰졌다면 디자인 승인 후 Capacitor Android 프로젝트 생성·debug APK 빌드를 통해 네이티브 UI를 검증하고, 마지막 기능 통합/릴리스 게이트에서 인증·동기화까지 실기기 테스트하세요.

## 특히 금지되는 것

- 사용자가 선택하지 않은 새 기능을 임의 확정하기
- 프로젝트 폴더 삭제·초기화·전면 재생성
- 검증 없이 대규모 의존성 교체
- 이미 확정된 데이터 관계·마감·시간 규칙 무시
- 실제 학습 기록 중복 허용, Drive 원본 삭제, 학원 시간을 자습 목표에 합산
- 보안키·OAuth client secret·토큰을 소스 코드나 Git 커밋에 포함
- 확인되지 않은 기능/테스트/배포를 성공했다고 보고

이제 저장소를 조사하고 **전체 UI·디자인 단계부터 실제로 작업**하세요.

## 실행 전에 파일을 놓을 위치

권장 구성:

```text
my-ipad-app/
  package.json
  docs/
    01_통합_기능_명세.md
    02_설계_결정_추적표.md
    03_Claude_Code_개발_계획.md
    04_Claude_Code_첫_실행_프롬프트.md

```

Windows PowerShell에서 작업 폴더 경로가 실제로 아래와 같다면:

```powershell
Set-Location 'C:\Users\USER\Projects\my-ipad-app'
claude
```

이미 다른 경로에 있다면 현재 실제 프로젝트 폴더에서 `claude`를 실행하세요. Claude Code 설치·로그인 상태, 명령어 이름은 사용자의 환경에 따라 확인이 필요합니다.
